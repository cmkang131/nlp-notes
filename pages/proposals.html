첫 번째 발표 : LLM Math Problem Solving

문제 : Code Generation 실패와 Thinking Cost

  • LLM이 수학·경시 문제를 자연어 token으로 바로 생성 : 도형이 이동·회전·반전되면 답을 못 만듦
    • 대신 program을 생성하고 도형 정보를 code에 넣어 계산
  • program 생성 방식의 두 실패
    • 관련 없는 tool·library를 주면 잘못된 code를 만들고, 오류를 탐지할 단서도 없음
    • thinking mode는 token을 많이 씀 : 120B급 model에서 thinking hard는 약 4배 token(토큰), accuracy는 약 9%p만 상승
    • (보충) model명은 transcript에서 GPT-OSs 120 billion으로 들림

방법 : 짧은 Solver Hint + Bridgehead

  • 정확한 solver(솔버) library·function 사용법을 짧게 hint로 줌
    • LLM이 optimal solver를 골라 code를 만듦
    • routing(라우팅) 문제 예 : hint 없이 23% → 짧은 solver hint로 83%
    • solver function 없이 긴 reference code만 주면 쓸모없는 function을 만들고 실패
  • bridgehead(브리지헤드) : 생성한 program을 문제의 예시 입력에 실행해, 알고 있는 예시 출력과 비교
    • exact answer·key가 없어도 됨, 비용 거의 없음
    • 예시가 맞으면 종료, 틀리면 그때만 thinking으로 반성·수정
    • 예시가 없으면 program 두 version을 만들어 간단한 입력에서 출력이 같은지 비교
  • 300개 경시 문제 실험 : 항상 thinking hard를 쓰는 것과 비슷한 accuracy, 훨씬 적은 token
    • (보충) 구체 token 수는 transcript 불명

Hint 검색과 Prior Work 차이

  • hint 검색 : model이 이전에 만든 문제·program 중 가장 유사한 것을 골라 재사용
  • prior work : 어려워 보이는 문제에 항상 thinking, 또는 언제 thinking할지 학습
  • 이 방법 : training 없음, verification 실패 시에만 thinking, model 자신의 program에서 짧은 hint 하나
  • 현재 범위 : 계산형 수학 문제
    • 향후 수학적 증명으로 확장하려 함

Q&A

  • 최근 LLM의 tool use와 차이 : tool을 단순 호출하는 것이 아니라, 문제에 맞는 tool을 효율적으로 찾는 데 초점
  • reward model·RL 대신 prompt(프롬프트)·input을 바꾸는 이유 : training·tuning 없이 open-source model로 결과를 내는 것이 목표
  • edge case : 예시로 걸러지지 않는 잘못된 답이 통과할 위험
    • 어려운 edge case는 예시만으로 해결하기 어렵고 추가 수학적 시도가 필요

Team 2 : Induction Head Recovery — Layer-Restricted Fine-Tuning

배경 : Induction Head

  • Transformer의 각 token은 attention(어텐션) head로 앞선 문맥을 참조
  • induction head(인덕션 헤드) : A, B가 나온 뒤 다시 A가 나오면 A 다음에 왔던 B를 찾아 예측
    • 이 복사 행동이 in-context learning의 핵심 기제
  • 주 induction head를 막으면 반복 token 예측 performance가 떨어짐
    • 다른 induction head와 추가 training으로 recovery(복구) 가능
  • prior work
    • CoEx : backup head가 primary head ablation을 partially compensate
    • Chabra 등 : corruption 후 retraining으로 circuit이 recovery
    • RoRA : 같은 parameter(파라미터) budget에서 layer별 LoRA capacity 배분이 performance에 영향

Research Questions

  • Q1 : early/middle/late layer만 각각 fine-tuning할 때 recovery 속도·정도가 어떻게 다른가
  • Q2 : recovery를 실제로 맡는 생존 head는 무엇인가
  • Q3 : 반복 길이·gap·shuffle·자연어처럼 training에서 보지 못한 입력에도 recovery가 generalization되는가

Experimental Design

  • model : GPT-2 small, 12 layer × 12 head, TransformerLens로 내부 분석
  • data : random token 전반부 + 그 반복인 후반부
    • metric : 후반부 NLL, top-1 accuracy, recovery rate
  • recovery rate : (damage 직후 loss(손실) − fine-tuning(미세 조정) 후 loss) / (damage 직후 loss − 원래 loss)
    • (보충) 1에 가까울수록 원래 performance를 많이 되찾은 것
  • induction head 찾기 : attention query·key vector의 곱으로 induction score, top-k head 선택
  • corruption : mean ablation(어블레이션), head 출력을 미리 계산한 평균으로 교체
  • Q1 : layer를 early/middle/late로 나눠 한 group만 fine-tuning
  • Q2 : ablation 직후·fine-tuning 후의 induction score, contribution, CoEx score 비교
    • contribution : head를 ablation했을 때 loss가 얼마나 오르는가
    • CoEx score : ablation 후 그 head의 contribution이 얼마나 커지는가
    • recovery를 맡은 head 집합이 겹치면 기존 backup path가 증폭된 것
    • 아니면 다른 backup path가 증폭된 것
  • Q3 : 반복 길이 변경, gap 삽입, 후반부 shuffle, 자연어 text의 네 변형

Q&A

  • layer를 3 group으로 나눈 이유 : layer별 영향을 보기 위해서, 무작위 분할이 아님
  • zero ablation 대신 mean ablation을 쓴 이유 : 0으로 만들면 영향이 과도해질 수 있음

Team 8 : Attention Head Pruning — Grammar Performance 보존

배경 : Pruning과 GQA

  • LLM(대규모 언어 모델) inference(추론) 비용 절감 : quantization(양자화), pruning(가지치기), knowledge distillation(지식 증류)
  • 이 팀 : attention head(어텐션 헤드) pruning, 일부 head를 제거해 parameter·latency를 줄임
    • head를 제거하면 efficiency는 좋아지지만, grammar 관계를 담당하던 head가 사라져 performance가 떨어질 수 있음
  • MHA(다중 헤드 어텐션) : head마다 별도 query/key/value
  • GQA(그룹 쿼리 어텐션) : 여러 query head가 key/value head를 공유
    • KV cache(KV 캐시) 감소 : KV head 8개 → 2개면 cached key-value 75% 감소

Prior Work와 빈틈

  • SAP : 구문 의존 관계로 pruning 후보를 고르고, candidate filtering으로 performance 하락을 제한
    • BERT-base를 6개 GLUE task로 평가, retraining 없이 pruning
  • 남은 질문
    • GQA의 shared KV 효과가 not verified
    • phenomenon별 grammar performance 변화가 not verified
    • 실제 efficiency(latency·memory)가 not verified
  • GLUE : task당 점수 하나 → 틀렸을 때 어떤 grammar가 무너졌는지 알기 어려움
  • BLIMP : minimal pair로 67개 phenomenon 평가 → phenomenon별 변화를 볼 수 있음

Hypotheses와 Experimental Design

  • H1 : phenomenon 간 importance는 겹치지만, phenomenon별 특화 head도 존재
  • H2 : 모든 phenomenon을 함께 고려해 head를 rank하면 worst-case performance 하락이 줄어듦
  • H3 : KV group을 통째로 제거하는 것이 query head를 하나씩 제거하는 것보다 더 아픔
  • model : LLaMA 3.2 1B, GQA, 16 layer, 총 512 query head
  • data : BLIMP minimal pair(미니멀 페어) 중 subject-verb agreement, anaphora agreement, determiner-noun agreement
  • importance : head를 하나씩 ablation해 grammar accuracy 하락을 재고, task×head 행렬을 만듦
  • pruning 전략 : random, single-task, multi-task
    • pruning ratio : 10%, 20%, 30%
  • metric : grammar accuracy, accuracy drop, pruning ratio, inference latency(지연 시간), memory usage
  • pipeline : baseline(베이스라인) → head masking → structural pruning → efficiency 평가
    • 자원이 허락하면 더 큰 GQA model로 확장

Q&A

  • grammar accuracy : BLIMP minimal pair에서 grammatical sentence·ungrammatical sentence의 log-likelihood를 비교
    • grammatical sentence가 더 높으면 correct, accuracy = correct 비율
  • SAP가 GLUE 9개 중 6개만 쓴 이유 : 일반 grammar 기능을 평가하는 대표 task 6개로 충분하다고 봄
